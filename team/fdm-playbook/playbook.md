# FDM Playbook — Audit, Findings, Workflows, and Reports

> **Status: living document.** This is the first module of the FDM playbook and covers the **Audit** phase of the Audit → Report → Act loop, plus how Findings feed into Workflows and the Report. The **Act** phase (Review Center, actions) is intentionally out of scope here and will be added in a follow-up module.
>
> The way Berlin works is evolving week by week — the *concepts* in this doc are stable, but specifics (UI surfaces, exact mechanics, what is and isn't automated) may change. Treat this as the current model, not a permanent spec.
>
> **Audience:** New and existing FDMs. Internal only. Refer to FDMs as "dedicated marketer" or "senior strategist" in customer-facing language; the FDM/Forward Deployed Marketer terminology is internal.

---

## 1. The mental model: Audit → Report → Act

Berlin's day-to-day operating model is a continuous loop with three phases:

1. **Audit** — observability. We watch the brand's SEO surface and surface findings.
2. **Report** — synthesis. We turn findings into a living per-brand document for the customer.
3. **Act** — execution. We turn findings into discrete actions that auto-execute or route through the Review Center.

This module covers everything an FDM does in the **Audit** phase and how that flows into the **Report**. The Act phase will be covered separately.

### The shift you need to internalize

The original premise was *"audit is automated, FDMs report and act."* In practice, **audit is rarely fully automatable** — there are too many branches and origins to cover with one autonomous loop, and the system has hard limits on agent loop counts. So:

- **Audit now has meaningful manual operation by the FDM.** You drive it; the agents help.
- **Everything you see under "up next" / "very soon" and below on the workspace home are workflows**, and for now treat workflows as **monitors only** — scheduled watchers, not general-purpose automations.

This may broaden in the future, but for the next several weeks: workflows = monitors.

### Nothing is on a schedule — the FDM triggers every loop

There are no scheduled agents in the system. Brand profile, files, findings, workflows, reports, actions, and skills are wired up so they *can* feed into each other through agent execution — but the agent execution itself is **always triggered manually by you**.

Concretely:

- Research happens because you start a Claude session (or invoke Berlin's agent).
- A finding is created or updated because you ask an agent (with the Agent Berlin MCP) to do it.
- A workflow is created, updated, or deleted because you ask.
- The report is modified because you ask.
- An action is created because you ask (covered in the Act module).

Skills (Section 3) encode *what* an agent should do once it's running — they do not start the run. Even a perfectly written skill is dormant until you launch an agent that uses it.

This will likely loosen over time (we may add scheduled agent runs), but right now: **the intelligence layer of the system advances when you advance it.** If nothing is moving, it's because nothing has been triggered.

## 2. The four bases of your work

Everything you do as an FDM is built on top of four artifacts that live with the brand:

| Artifact | Source | Used for |
|---|---|---|
| **Brand profile** | Auto-generated by Berlin during onboarding; verified/corrected by the brand | Grounding every downstream decision |
| **Files tab** | Free-form uploads by the brand | Anything that doesn't fit Berlin's structured schema (e.g. "focus on these 100 keywords") |
| **Findings tab** | Created and curated by you (or by agents, on your behalf) | Your research output — the base of everything downstream |
| **Workflows (monitors)** | Created by you with agent help, based on Findings | Continuous observability; produces fresh data on a cadence |

The Report is then **derived** from these four. Actions (next module) are derived from all of the above plus the Report.

### A note on Brand Profile

Brand Profile is filled automatically during onboarding using multiple research agents (Perplexity, Gemini, etc., then collated into structured form). It contains overview (with sub-fields like business model and customer segment), narrative, USP, differentiation, geographies (primary + secondary), competitors, topics, and so on. A **topic** is a keyword cluster representing something the brand stands for. The brand owner is expected to verify and correct it — they often haven't yet, so when something looks off, don't assume it's authoritative.

**Every brand profile is injected into an agent's context at runtime.** Anywhere an agent runs against the brand, it sees the brand profile by default. That's why getting it accurate matters: errors propagate into every downstream agent decision.

### A note on Files vs. Findings

- **Files** are for the *brand* to upload anything that doesn't fit Berlin's structured schema. Common examples: a **user-persona document** (we don't have a structured Persona schema in Brand Profile because Personas aren't a universal SEO concept — different brands use them differently or not at all), a brand tone-of-voice guide, or any onboarding artifact the brand wants the agent to respect.
- **Findings** are for *you and the agents* — never the brand. The brand can read findings but cannot edit them.

Files and Findings also have different lifecycles: a Brand Profile file tends to be long-lived (it's reference material for the brand), whereas a finding's life cycle is usually over once that finding has run its course (e.g. an investigation into a specific GSC issue, once resolved).

## 3. Skills — the cross-brand instruction layer

Sitting alongside the per-brand artifacts above is a separate fundamental concept: **skills**. A skill is a reusable set of instructions that tells an LLM (Berlin's agent or Claude with the Agent Berlin MCP) what to do, where to do it, and how. **A skill does not belong to a project** — it lives at the system level and can be reused across brands.

### What a skill can be

Skills span a wide range of granularity:

- **Broad strategy.** "How to do an audit" — which itself decomposes into smaller skills like keyword research, cannibalization checks, etc.
- **Mid-level.** "How to do keyword research."
- **Granular.** "How to check a single URL's position in Google Search Console."
- **System-usage skills.** Instructions for how to use Berlin's internals in a specific way. Example: if you've built a custom onboarding format where the brand fills out a particular questionnaire and you save the answers as a file in the brand profile, a skill can encode "for this kind of brand, read that file from the brand profile and use it to shape every workflow / research / action you take."

Skills are how you teach the system to do strategy consistently *or* to use the platform in a specific, repeatable way.

### Skills don't fire themselves

A skill is just instructions — it executes only when an agent is launched with that skill in context. Combined with the [orchestration note in Section 1](#nothing-is-on-a-schedule--the-fdm-triggers-every-loop), this means: **a great skill stays dormant until you trigger an agent that uses it.**

### Skills vs. per-brand artifacts

Findings, workflows, and reports are bound to a single brand. Skills are not. When you find yourself encoding "how we do X" rather than "what's true for brand Y," that's a skill, not a finding.

## 4. Findings — the core artifact you produce

> **The most important concept in this playbook.** If you don't internalize this, you'll make a lot of preventable mistakes.

### What a finding is

A finding is a research artifact you create about the brand. Each finding has:

- A **title**
- A **short description** of what the finding is
- A **body** with the actual content (analysis, data, evidence)

### Why findings exist (and where they fit)

Findings replace the old habit of sending research outputs over WhatsApp or scattering them across files. **Everything you find during research belongs in a finding** — it's the single place where your work persists in a form Berlin and Claude can use.

### How findings are surfaced to agents

This is the part to understand carefully:

- **Title and description are always exposed to the agent at runtime** (Berlin or Claude). The agent sees all findings every time it runs.
- **The body is fetched on demand.** The agent reads the body only when title+description suggest it's relevant.

**Implication:** If you have a *thousand* findings, you'll fill the agent's context with titles+descriptions alone and degrade its ability to work. Be deliberate — don't create findings just to capture every thought.

### Where findings can be edited

- **Only through Claude (with the Agent Berlin MCP) or through Berlin's agent.** There is no UI to edit findings, on purpose — the UI is what customers see, and we don't want them editing findings.
- **In Claude:** always include the prefix `Use Agent Berlin MCP` in your prompt. That tells Claude to use the MCP that knows how to read, list, and modify findings.

Example: `"Use Agent Berlin MCP — list all findings for project X"` → Claude returns the list. Then ask it to update or create new ones.

## 5. Working with findings day to day

### Cadence

- **Typical: 1–2 new findings per day.** Some days zero. Occasionally more, when something needs to be broken into pieces.
- You'll also be **updating existing findings** as you learn more.

### Workflow when multiple Claude sessions feed one finding

You'll often run research across multiple parallel Claude sessions (different tangents, or splitting work to save tokens). To consolidate cleanly:

1. In the first session, ask Claude to **summarize its findings into a `.md` file**.
2. **Verify the `.md` has everything important.** Claude will sometimes drop things to save tokens. Add back what's missing. Also remove anything that *isn't* important — we're trying to stay token-efficient.
3. Open the next session and tell it: *"I already have an `.md` file with the findings so far — please add your findings to the same file."*
4. Repeat for every session feeding the same finding.
5. When the `.md` is complete, ask Claude (with `Use Agent Berlin MCP`) to **update or create the finding in Berlin from this file.**

> **Tip:** This `.md` → finding pipeline keeps findings clean and lets you control exactly what ends up in Berlin's context.

### When to update vs. create vs. archive a finding

There is **no rigid rule.** Use judgment. Guidelines:

- **Update an existing finding** when new research belongs to the same topic (e.g. on-page SEO that you re-audit monthly — update the same file).
- **Create a new finding** when the topic genuinely doesn't fit anywhere existing, or when a single file would get too large to stay useful.
- **Archive a finding** when it's stale or fully superseded.

Both "update the existing on-page audit finding" and "archive the old one and create a fresh audit finding" are valid. Pick whichever keeps things organized.

> **Don't agonize over this.** Creating an extra file when one would have done costs almost nothing. Forgetting to split causes minor friction, not real problems. **Be sensible, but a mistake here is recoverable** — just stay organized as you go.

## 6. When NOT to create a finding

Not all research deserves a finding. The test is roughly: *can this data be live-fetched from a source cheaply, any time it's needed?*

- **Don't create a finding** when the data is something an agent can pull live on demand. Example: Lighthouse performance scores — those can be live-fetched from the Lighthouse API at runtime, so there's no point storing them as a static finding.
- **Do create a finding** when the data is the result of *analysis across multiple data points* — i.e. you did real research, not just a pull. That kind of work is worth persisting.

### Exception: expensive fetches

If the data is *cheap* to live-fetch, skip the finding. If the data is *expensive* to fetch and you'll need to reuse it many times, **persist it as a finding** to avoid re-paying the cost.

- **Example:** A Google SERP analysis for 2–3 queries → still cheap, skip the finding.
- **Example:** A Google SERP analysis for 1000 queries → expensive, persist as a finding.

We don't have many super-expensive calls today, but use this rule when one shows up.

## 7. Workflows (monitors) — derived from findings

### What a workflow is, right now

Workflows are **scheduled monitors**. Each one is a script that:

- Polls a slice of the brand's SEO surface on a cadence,
- Pulls data from one or more sources,
- Performs aggregations/collations,
- Saves a structured report **for agents to consume next time** (not human-readable).

You can also run a workflow manually via the "run now" button on its card.

> Workflows *may* become more general-purpose in the future. For now, treat them strictly as monitors.

### What a workflow is, technically

A workflow has four parts at creation time:

1. A **Python script** — the actual logic that executes.
2. A **schedule** — when the script runs.
3. An **infra spec** — which machine to run on, how long it's allowed to run, and other runtime settings.
4. An **output spec** — a description of the JSON the script will produce, attached to the workflow itself.

Every workflow run produces **a JSON file, or it errors out.** JSON is the only output channel.

The JSON is **written for agents to consume, not humans.** It can be very large. An agent reads the output spec first to understand the shape of the output, then decides whether to load the full payload. Humans *can* read the JSON, but they're not the intended consumer — the report is where this data ends up in a human-readable form.

> A workflow is a plain Python script; it has no built-in intelligence layer. The intelligence comes from an agent (which you trigger) reading the workflow's output and reasoning over it.

### How workflows are surfaced in the workspace

- Cards on the home view = workflows running soon (today/tomorrow).
- The table below the cards = workflows not running in the next two days.

### Creating workflows from findings

Every time you create or update a finding, ask yourself: *does this finding warrant a new monitor, an update to an existing monitor, or nothing at all?*

The iterative approach:

1. After updating findings, ask Claude (with `Use Agent Berlin MCP`): *"Look at the findings and tell me what workflows / monitors I should set up."*
2. Claude will return a list of candidate workflows.
3. **Review every candidate.** Discard the ones that aren't actually useful — keep only ones that monitor something you genuinely want to watch over time.
4. Ask Claude to create the ones you approved. It will schedule them automatically.

> ⚠️ **Never blindly accept what Claude suggests.** This applies everywhere, but especially here. Claude will happily produce 12 workflows when only 8 are useful. Always review, prune, and verify.

> ⚠️ **After a workflow runs, verify its output.** Click into the workflow, look at the report it produced, and confirm it's actually monitoring what you intended. A workflow that runs successfully but watches the wrong thing is worse than no workflow.

### Modify before creating

If a new finding *almost* fits an existing workflow, **update the existing workflow** instead of creating a new one. Avoid sprawl.

## 8. Reports — derived from everything above

Once you have brand profile, findings, and workflows, the next phase is the **Report**.

### What the report is for

The report has two jobs:

1. **Give the customer the current status of their SEO** — what we're working on, the major issues, the state of things.
2. **Keep us accountable.** The customer can see if a known issue has been sitting unresolved for a long time and ask why.

### What's in the report

Reports combine:

- **Static information** pulled from findings.
- **Dynamic information** that updates automatically as workflows run and produce fresh data.

### Report structure

- Multiple pages (overview, issues, fixes, etc.) accessible from the left tab.
- **Nothing in the report is fixed.** Pages can be added, removed, or restructured per brand.
- When an issue is resolved, **remove the page that tracked it** — keeping it adds noise.
- When a new significant issue surfaces, **add a page or component** for it.

### Editing the report

Same rule as findings: the report is shaped via Claude (with `Use Agent Berlin MCP`) or Berlin's agent. The customer sees the report; they don't edit it.

## 9. Putting it all together — a day in the life

A rough mental loop for a working day:

1. **Open Claude session(s)** for the project. Use the `Use Agent Berlin MCP` prefix.
2. **Do research** — open tangents in parallel sessions when useful, save tokens where possible.
3. **Consolidate into a `.md` file** per finding topic, across sessions.
4. **Verify and trim** the `.md`. Be deliberate about what makes it in.
5. **Push to Berlin as a finding** (new or updated) via Claude + MCP.
6. **Ask Claude: do my new findings warrant new/updated workflows?** Review its suggestions; prune; approve; create.
7. **Check that recently-run workflows produced sensible output.** Spot-check.
8. **Update the Report** if any of today's work changes what the customer should see — add/remove pages, update sections.

> Findings are the base of everything. If your findings are organized and accurate, workflows and reports follow naturally. If findings are messy, everything downstream is messy.

## 10. Tips, warnings, and reasoning to internalize

A consolidated list of the small rules that prevent big mistakes:

- **Always include `Use Agent Berlin MCP` in Claude prompts that touch Berlin findings/workflows/reports.** Without it, Claude doesn't know how to reach Berlin's data.
- **Findings live only behind the MCP / Berlin's agent — there is no UI to edit them.** This is deliberate (we don't want customers editing them).
- **Title + description of every finding are always loaded into the agent's context.** Keep them concise and specific. The body is fetched on demand.
- **Don't dump everything into findings.** Too many findings = degraded agent performance. Aim for 1–2 a day, sometimes zero.
- **Don't create findings for live-fetchable data** (e.g. Lighthouse). Exception: expensive fetches needed many times.
- **Never blindly accept what Claude generates** — for findings, workflows, or report changes. Always review, prune, and verify.
- **After a workflow runs, verify its output is actually useful.** A confidently-running but wrong workflow is worse than no workflow.
- **Be organized with finding files, but don't agonize.** Creating an extra file or missing a split are both recoverable.
- **Update existing artifacts before creating new ones** — finding, workflow, or report page. Avoid sprawl.
- **Free-form `findings` content is fine** — there's no required structure. Use sections and frameworks if they help you and the agent reason about it later; skip them if they don't.
- **Workflows are monitors, for now.** Don't try to use them for one-off tasks.
- **Reports keep us accountable.** If something has been a known issue for weeks and the report still surfaces it, that's a signal we need to act, not hide it.
- **Bring product feedback.** If something about Berlin makes the FDM workflow harder, surface it — FDM feedback is part of the role and shapes the roadmap. But: collect feedback and let priorities sort it; not every issue needs to be fixed immediately.
