Who is in the system

Five components, and the line between them

Nothing here is new architecture. Classification adds endpoints to layers that already existed — but the split of work between them is deliberate, and it is the thing to learn first.

bifrost UI

React + TypeScript · browser

The operator's screen. Every action that changes what the corpus and the topics are is a button here, on a screen that shows what will change before it is pressed.

  • Parses the CSV in the browser
  • Shows "your topics have changed"
  • Owns Sync topics and Build

Berlin backend

Go + Postgres · always-on

The product database, and the source of truth for topics. Customers create and edit them here. It also hosts /aeo, the narrow door the agent talks through.

  • Stores topics: name, description, parent
  • Computes the two
  • Serves /service to bifrost

bifrost proxy

Go · always-on

The front door to bifrost, and increasingly a reader in its own right. It answers from shared storage without waking anything, and it owns the placement table that decides which machine a job lands on.

  • Answers all ingestion: upload, topic sync
  • Serves status, sample, verdicts, unprocessed
  • Runs the in Go
  • Routes builds→GPU, everything else→CPU

bifrost worker

Python · GPU (scale-to-zero) or CPU

Where models and indexes live. Two flavours of the same code: one GPU machine cluster-wide that scales from zero to run builds, and a 16 GB CPU worker that runs assign.

  • GPU: , index, scoring
  • CPU: assign — tiers 1 and 2
  • Holds no Berlin credential

The LLM agent

aeo SDK + CLI → /aeo

Owns what the keywords mean. It reads state, judges a few hundred keywords, and writes the answers back. It cannot upload, build, or sync — those are a human's to press.

  • status · sample · verdicts
  • assign · unprocessed

The line that explains the whole surface

The human owns what the corpus and the topics are. The agent owns what the keywords mean.

Upload, build and topic sync are operator buttons. Judging whether a keyword belongs to a topic is the agent's. That single line predicts, for any new endpoint, which side of the wall it belongs on.

The whole flow

Ingestion derives nothing; one job derives everything

The pipeline turns on a single distinction, and it is worth getting before anything else. Bringing data in — a keyword upload, a topic sync, a GSC sync — writes down what it was given and stops. Deriving anything from it — prototypes, an index, scores, assignments — happens only in a job somebody explicitly triggered.

That is the invariant being protected: nothing derived happens by surprise. It also means every derived file has exactly one writer, which is what lets these jobs sit on different machines without a lock between them.

Stage 01 · Berlin

Topics live in Postgres, and stay there

Berlin A topic is a row the customer owns: a name, a one-or-two-sentence description, and an optional parent. That is the source of truth, and nothing in bifrost ever writes back to it.

The description is not decoration. A name alone — "Running" — is a weak anchor for an embedding; name plus description is what actually gets turned into a vector two stages from here. Onboarding writes the first draft and the customer edits it.

Two fingerprints, because two different things go stale

Every topic is hashed over exactly the content that would invalidate downstream work — name, description, parentage — and nothing that would not. Those per-topic hashes roll up into one set-wide hash. One hash function used at two scales, so the two can never disagree about what counts as a change.

FingerprintMoves whenWhat it protects
set.fingerprintanything in the set movesPrototypes, scores and assignments — all of which weigh every topic against every other, so a new column can change any keyword's best topic. Redone whole, and cheaply.
topic.fingerprintonly that topic's own name, description or parent moves — the expensive axis. Adding a sixteenth topic must not cost the other fifteen their labels.

Sitting alongside them is the — a counter (v3) stamped when the set-wide fingerprint moves. Content decides what is still valid; the counter is what a person can read. "Computed against v2, current is v3" is a sentence a human or an agent can act on; a content hash gives no ordering, because a revert produces an older hash.

The leaf rule — which topics actually compete

Topics are a one-level tree. Classification targets the : every child, plus any parent that has no children. A parent with children never competes as its own prototype — its vector would be a near-duplicate of its own children's, which is exactly the failure the health check exists to catch, and its keyword set is definitionally the union of theirs.

Parents are still sent in the payload, because the tree is what the customer sees and a rollup that cannot name its parent is a rollup nobody can read.

// backend/internal/topicset/topicset.go
type Topic struct {
    Value       string   // no row id — bifrost keys everything by value
    Description string
    Parent      string
    Leaf        bool     // competes for keywords
    Fingerprint string   // what labels are filed under
}

Stage 02 · Proxy

The freshness check that wakes nothing

Proxy When someone opens the keyword screen, the proxy asks Berlin for the current set-wide fingerprint and compares it with the one stored beside the brand's keyword index. One HTTP call, a 10-second timeout, no model loaded, no machine started.

That featherweight-ness is the whole point. It runs on every page load, so change is always visible and never surprising: the UI can say "the topics in the dashboard have moved since these keywords were classified" without anything spinning up. If Berlin is briefly unreachable the page still renders what it knows and says what it could not check — a page that shows nothing because a backend hiccuped is worse than one that is honest about the gap.

A mismatch never auto-resolves

A changed fingerprint shows the user their topics have changed. It does not silently re-sync anything.

The user resolves it with a button on that same screen. Change is visible, and resolving it is a person's decision — because a sync followed by a build re-stamps the version every existing assignment records having been measured against.

Stage 03 · UI → Proxy

Sync topics: one request, one file, nothing derived

UI Proxy Pressing Sync topics is the only way a sync ever happens — no agent, no schedule, no other screen. And it is smaller than it sounds: one request to Berlin and one file write. No model is loaded, no worker is woken, and nothing is derived.

The proxy already holds BERLIN_SERVICE_TOKEN and already calls that exact endpoint on every page load for the freshness check, so the button is as fast as the backend's answer. What it writes is Berlin's payload verbatim, to classification/topic_pull.json.

Two files, because they have two different authors

The pull and the set in force are deliberately separate files rather than one document two things write to:

FileWritten byWhat it is
topic_pull.jsonProxyBerlin's payload as sent. The topics the customer has right now.
topic_set.jsonBuildWhat a build actually embedded, naming the pull it was built from, with the version stamped.

Comparing the two answers "is a build due?" from two local files, with nothing to ask anyone — and neither side ever read-modify-writes the other's work. It is also the shape that survives the planned move to an admin UI: when bifrost is eventually pushed to rather than pulling, a push replaces one proxy handler and nothing else. A pull that lived inside the build would leave no door to replace, and would park a backend credential on the GPU permanently.

A mismatch never auto-resolves

A changed fingerprint shows the user their topics have changed. It does not silently re-sync, and syncing does not silently rebuild.

Both are buttons, because the version a build stamps is the version every existing assignment records having been measured against.

Stage 04 · Proxy ingests, GPU derives

Upload on the proxy, build on the GPU

UI Proxy The CSV is parsed in the browser — counts shown, nothing sent until the operator presses the button — and the append is answered by the proxy. Two rules make the corpus cheap:

  • Uploads append. Re-sending a known keyword is a no-op. No upload can delete a keyword.
  • Builds add, never wipe. Already indexed → skipped. New → embedded and indexed. Re-running with nothing new is a no-op.

The upload sits on the proxy for a reason that is latency, not cost: a thirty-second worker task is fractions of a cent, but on a worker the upload can sit behind a cold start — and this is the button people press most. The one part that scales with the corpus is the dedup set held in memory while the batch is checked against it, roughly 150–200 MB for a million-keyword brand. That is the same shape as the intent read the proxy already serves, and it takes a slot from the same scan budget.

It is also the one job in the system that reads what it writes, so it needs ordering rather than just a single writer. The proxy's per-brand single-flight lock provides it: two uploads for the same brand cannot interleave, and the second gets a busy response and retries.

The build is one job with three steps, and the order is load-bearing

GPU worker A build ends "prototypes current, indexed and scored":

  1. Put the pulled topics in force — a per leaf topic, the , the version stamp.
  2. Embed and index the new keywords — the only step that genuinely needs a card.
  3. Score the corpus against the prototypes now in force.

Prototypes first, so the scoring at the end is against the topics in force; the index second, so that same pass sees the keywords this build just added. Both of the things that can invalidate a score are settled before the score is computed — which is why there is no second job and no handoff.

Prototype embedding does not need a GPU on its own merits; it is a few dozen short texts. It is here because it invalidates the scores, and the scores are the build's to write. Keeping the writer singular is the point; the card is incidental. That is also why the version is stamped here and nowhere else: stamping it in a job that might then fail to score would leave a version in force that nothing on disk is scored against — a state that reads as current and is not.

The GPU needs no credential for any of this. The build reads the stored topic pull off shared storage and never contacts Berlin, so no worker task definition carries BERLIN_SERVICE_TOKEN.

Placement is two rules, and welding them was the original mistake

"The build writes derived data, and the build runs on the GPU" reads as one rule. Once welded, the GPU starts to look like an ownership boundary, and every new piece of derived data has to argue for a card it does not need. They are separate:

Axis 1 — what may write derived data. Only an explicitly triggered job. Never as a side effect of ingestion, never by a read.

Axis 2 — which machine. The GPU if and only if the job runs the embedding model over the corpus. Everything else runs where it fits. Hardware economics, carrying no meaning about ownership.

assign is the case that proves they are separate: it writes derived data, so it is explicitly triggered; it runs no model, so it is not GPU work. And it cannot ride the build under any arrangement — the first build for a brand happens before a single calibration label exists, so there are no bars for tiers 1 and 2 to apply.

// bifrost-proxy/internal/handlers/placement.go

// everything else that reaches a worker → CPU.

Stage 05 · Worker

Scoring: one matrix multiply, at the tail of the build

GPU worker This is the arithmetic half, and it is the cheapest step in the system. Every keyword vector is multiplied against every topic prototype. Because both sides are L2-normalised, the dot product is the cosine similarity. For each keyword the pass records four things and nothing else: its best topic, that score, its runner-up, and the between them.

No bar is applied here. Nothing is assigned. Scoring only produces the numbers that calibration and the tiers later read.

Rule · scoring is never a job

Scoring never gets its own trigger, its own job or its own machine. It is the last thing the build does before it exits.

Two things can change the score matrix — new keyword vectors and a new topic set — and both are now steps of the same build, settled before step three runs. So the pass happens once, at that build's tail. Repair needs no special verb either: scoring skips what already has a score against the current version, exactly as indexing skips what is already indexed.

It is on the GPU by inheritance, not by merit. This is a numpy matmul against a matrix that never exceeds a hundred columns; it would run at the same speed on a CPU. It is here because the build owns the derived files, and an earlier draft that put it on a separate topic-sync job made that job a second writer of the score files — an overlap that had to be papered over with a cross-machine mutex, and one of two ways status came to report a corpus as scored when it was not.

Stage 06 · Worker writes, Proxy serves

The sample pool: choosing what is worth judging

Worker Before it exits, the scoring pass writes a second, much smaller file: up to 400 candidates per topic, chosen from across the score range. This is the file sample later slices.

It is written here for the same reason scoring is: picking which keywords are worth an LLM's judgment means looking at every keyword's score, which is a full pass over the corpus. Doing it once, on the machine that has just finished that pass anyway, turns sample into a prefix of a small file — a genuinely free read on the always-on side, rather than a million-row scan every time an agent asks for something to label.

The pool's shape, and the one judgment in that module

Sorted by score, a topic's keywords are boring at both ends: the top of the range is obviously the topic and the bottom obviously is not, so labels spent there buy nothing. The bar sits in the fuzzy middle, so that is where the labels go.

Stage 07 · Agent → Proxy

Verdicts: a few hundred yes/no answers

Agent Proxy The agent calls sample, gets back (keyword, best-topic) pairs, and answers exactly one question per pair: does this keyword really belong to this topic — yes or no? Never "rank these topics." A per-topic yes/no is what makes a genuinely multi-topic keyword expressible as two independent yeses.

Those answers go back through verdicts into an append-only cache. The cost is a few hundred quick judgments per brand — not one call per keyword.

Keyed by (keyword, topic fingerprint) — the load-bearing decision

Every verdict carries the score it was judged at, and that score is a cosine against one topic's prototype. Edit that topic's description and the prototype moves, so a label recorded at 0.83 now belongs to a keyword scoring 0.71. Sweeping both into one bar fits a threshold across two coordinate systems and produces a plausible, wrong number with nothing to catch it. The label can also stop meaning what it meant: rewrite "road running shoes" to "all running footwear including trail" and a no becomes a yes.

None of that is true of a topic nobody touched. So the key is the topic's own fingerprint, not the set version — and that turns "only the affected topics are re-labelled" from a predicate someone has to evaluate into a path on disk:

classification/verdicts/
├── a3f9c1…/   Running Shoes, untouched → all 112 labels still here
├── 7b21e4…/   Trail Running, untouched → 94 labels still here
└── e0d4aa…/   Barefoot, description edited → fresh, empty directory
                         the old 88 labels are not deleted — they sit
                         under the old hash, and a revert finds them again
  • An untouched topic resolves to the directory it always did.
  • An edited topic resolves to a fresh empty one, and reads as unlabelled.
  • A reverted topic hashes back to its own labels and finds them waiting.
  • Nothing is ever deleted to make any of that true.
Why it is one file per batch, not one file appended to

This store is written by the always-on proxy and read by both the proxy and the worker, on a shared filesystem, with no lock between them. Appending to a single file across two machines risks interleaved lines. A file per batch cannot interleave, cannot half-append, and makes a crashed write a file that is simply skipped.

Re-recording is idempotent — reads keep the newest record per key and drop the rest — which is what makes the whole surface safe to retry.

One store, three writers, and that is deliberate: a verdict is the same fact wherever it comes from. In calibration the bar is not set yet, so the verdict is evidence for where it goes. In tier 3 the bar was applied and came up empty, so the verdict is the assignment. In verification the keyword is already filed, so it is a confirmation. A keyword labelled during calibration that resurfaces in tier 3 is already answered, for free.

Stage 08 · Proxy (Go) and Worker (Python)

The sweep: where the bar actually comes from

This is the step the whole design turns on, and the one whose name explains the least. Here is what it does.

A cosine from the embedding model lives in a narrow band that shifts from brand to brand and from topic to topic, so 0.85 is neither strict nor lenient until this brand's own keywords say which. A hardcoded bar is a precision nobody measured, applied to a corpus nobody looked at.

So instead: take one topic's labelled (score, yes/no) pairs, sort them by score, and the range. At every stop, measure the precision you would get — the share of labels at or above the bar that were a yes. Take the lowest bar that still meets the target, because every step down admits more keywords, and the point is coverage at a stated accuracy rather than accuracy alone.

The shortlist is stratified, so counting labels plainly measures the wrong thing

Here is a bug that lived in this code, and it is worth understanding because it is the kind that survives review: both halves were individually correct.

The shortlist deliberately takes fewer keywords from the top of the range, where the answer is obviously yes, and more from the middle, where the bar sits. That is the right way to spend labels. But it means the labels are a , not a uniform draw — and the sweep was counting them as though they were uniform.

The top quintile holds 20% of a topic’s keywords and supplies 10% of its labels; the middle quintile holds 20% and supplies 40%. So the region with the highest yes-rate is counted at half its true weight and the murky middle at double. Measured precision therefore comes out lower than the corpus would actually deliver.

Take a topic whose five bands run 100%, 95%, 70%, 30%, 5% yes, and a bar admitting the top three:

Band, by scoreShare of the topicShare of the labelsYes rateWeight
1 · top20%10%100%0.20 / 0.10 = ×2.0

3 · middle20%40%70%0.20 / 0.40 = ×0.5

5 · bottom20%10%5%×2.0
 
what the corpus actually delivers   (100 + 95 + 70) / 3                      = 88.3%
counting the labels plainly         (10·1.00 + 20·0.95 + 40·0.70) / 70         = 81.4%   6.9 points low
weighting each label by its band    (20·1.00 + 20·0.95 + 20·0.70) / 60         = 88.3%   the correction is exact

Three consequences, and only the last one is obvious:

  • The bar lands higher than the target needs, because the sweep keeps walking up looking for a precision the sample structurally cannot show it.
  • Fewer keywords get filed — coverage paid for an error nobody could see.
  • The reported precision was not the precision assignment would deliver. The error is in the safe direction, which is exactly why it survived: nothing broke, and the headline number was simply wrong.
The correction

Each label counts for its band’s share of the topic divided by its band’s share of the labels — the standard estimator for a stratified sample.

Every pool row now carries band and band_share; the verdict copies both; the sweep weights each label on the worker and the proxy alike. support and positives stay plain counts, because they say how much evidence there was, not what it measured — and over a topic whose labels reach every band the weights sum to its label count, so is untouched. Weighting changes what a label says, not how much evidence the topic brings.

Two rules came with it, and both are about refusing to half-apply a correction:

  • A label with no band is not evidence. It is dropped from the sweep entirely rather than counted unweighted — a correction applied to some labels and not others is worse than none, and nothing quietly switches a topic back to the old arithmetic.
  • Only calibration verdicts are swept. Any verdict whose pair is in the pool picks up a score whatever its source, so once tier 3 lands, a tier-3 verdict on a pool keyword would have walked into the calibration evidence on the strength of that score alone. Source, not the presence of a score, is what makes a label evidence.

One number on this page still needs reading carefully. Coverage — when you see it quoted against a sample rather than a corpus — is the share of the labelled shortlist a bar claims, not the share of the corpus. The shortlist is middle-heavy by construction, so it over-represents borderline keywords; a bar that claims a quarter of the shortlist still claims most of the keywords that actually score high. That is the same stratification, read on the other axis.

Read that coverage number carefully. It is the share of the labelled sample the bar claims, not the share of the corpus — and the two are deliberately different. The sample pool is concentrated in the fuzzy middle precisely because that is where the bar lives, so it over-represents borderline keywords by construction. A bar that claims a quarter of the sample can still claim most of the keywords that actually score high.

Two properties of that walk are easy to miss and both are in the code:

  • Precision is not monotonic in the bar, so the sweep walks the whole list and keeps the deepest qualifying point rather than stopping at the first dip.
  • A cut is only considered between distinct scores. A bar that splits two keywords with identical scores is not a bar the assignment step could apply.

And when a topic cannot reach the target on any cut — not even its single highest-scoring labelled keyword is a yes often enough — the answer is nil. That is a real finding about a topic and is reported as one; the caller falls back to the brand-wide bar rather than inventing a number.

What the agent names, and what it does not

The agent says "96% precision". It never says "0.83".

The target travels with the call as an argument; nothing on disk stores a threshold. There is deliberately no set-threshold endpoint, because a saved threshold is a number that drifts out of step with the topic-set version it was measured against — and this way there is nothing to drift.

Stage 09 · Proxy / Worker

Shrinkage: what to do about a topic with nine labels

Budgeting ~100 labels per topic is affordable because there are fifteen topics, not a thousand. But the budget cannot fix a topic the corpus is thin on: a topic owning 40 keywords cannot yield 100 labels however much we are willing to spend.

Fitting a bar to what it does yield is worse than not splitting at all — a bar set by noise misfiles every keyword near it. So each topic's measured optimum is toward the brand-wide bar in proportion to the evidence behind it:

bar = (n · own_bar + k · brand_bar) / (n + k)        k = 20

Continuous, with no minimum-label cutoff to argue about. And the reported precision is re-measured at the shrunk bar, never carried over from the sweep — because the shrunk bar is the one that will actually be applied, and reporting the precision of a bar nobody uses is how a system ends up with a measured accuracy that is not the accuracy anyone gets.

Stage 10 · CPU worker + Agent  Shipped

Assignment: three tiers, cheapest first, and an honest remainder

Everything up to here is measurement. assign is the call that writes topics onto keywords. It derives each topic's bar from the recorded verdicts at the target the call names, then walks every keyword in the inventory. No LLM runs inside it — all the language work sits on either side: judging the sample before, settling the remainder after.

It is the one classification verb with no button, and deliberately so. The only judgment in it is the precision target, which the design keeps an argument, not stored state. A UI button would have to get that number from somewhere — hardcode a default, which is a precision nobody chose, or persist the last one, which is the drifting state the design refused. The target is also chosen from what status just reported about per-topic bars, which is agent context.

A recorded no is a veto, at every tier

Whatever loop wrote it, a judgment that this keyword does not belong to this topic outranks a score above the bar and a neighbourhood agreeing.

The veto used to apply only to tier 2, so a keyword the embedding put confidently in the wrong place was re-filed under the denied topic on every run — and the phase-4 verification pass would have asked about it forever. It now vetoes the (keyword, topic) pair rather than the keyword: a denied runner-up drops the second topic and leaves the primary standing; a denied primary sends the keyword to the tiers that ask rather than infer. It does not promote the runner-up in the primary's place even where that runner-up clears its own bar — what a denial contradicts is the ranking tier 1 stands on.

It is applied inside tier 1 rather than at the moment of writing, because the map tier 2 votes from is built out of what tier 1 filed: a keyword nobody should have filed must not go on to be evidence for filing its neighbours.

Why assign runs on the CPU worker

Tiers 1 and 2 are a single pass and cannot be split — tier 2 propagates from what tier 1 filed, so it reads tier 1's output. It is not GPU work in any sense: hnswlib is CPU-only, with no CUDA build anywhere in this stack, so a card would run tier 2 at exactly the same speed, after a cold start, on the one instance builds queue for.

And it is not proxy work, for a concrete reason. hnswlib stores the vectors inside the index: at M=64 and 1024 dimensions that is roughly 4.6 KB per element — about 1.15 GB at 250k keywords and 4.6 GB at a million. The proxy has 2 GB in total, shared with the UI. Tier 1 alone would fit; tier 2 does not, and not by a small margin. So: the CPU worker, where there are 16 GB.

assign needs one guard and has it: it refuses while a keyword build for the brand is running, because a build's tail rewrites the score table it walks and appends to the index tier 2 queries. It is a refusal before anything is read or written, not a lock — the proxy's single-flight lock cannot cover this, since that lock covers the request that starts a build, not the build, which runs on for minutes on another machine.

Multi-topic, and how we know it is real

Ranking always produces a second place, so "has a runner-up" means nothing — every keyword has one. The test is that both topics independently clear their own bar: topic B would have confidently claimed the keyword even if topic A did not exist.

  • "protein powder for weight loss" scores above the bar against both Protein Supplements and Weight Loss → two owners.
  • "running shoes for women" scores high on one topic while its runner-up sits far below that topic's bar → one owner, and the runner-up is never shown as anything.

The definition self-limits: in a healthy topic set only a small slice of keywords clears two bars. If a large share does, that is not a multi-topic corpus — it is the health check telling us two topics overlap and should be merged.

The one duplication we chose

The sweep is written twice, on purpose

Go Python status must answer without waking a worker. assign runs on the worker and needs the same arithmetic. So the sweep, the shrinkage and the point selection exist twice: in Python on the worker and in Go on the always-on proxy, constants included.

They are held together by test cases that mirror each other name for name. A change to either side that does not land on both makes a topic's bar depend on which door you read it through — and the mirrored test is what fails first.

That is not theoretical. The three highlighted pairs below landed with the band-weighting fix, hand-computed on both sides — the mechanism working as intended, rather than one implementation quietly drifting ahead of the other.

The collapse we deliberately did not take

assign could fetch its bars from the proxy's status rather than computing them, leaving Go as the only implementation. It only works in that direction — dropping the Go copy would mean waking a worker to answer status, which the design forbids.

It trades a duplication that a test catches for a worker-to-proxy dependency on a number the worker has every input to compute locally. Worth revisiting if the sweep ever needs changing more than once; not worth doing pre-emptively.

The agent's door

One group, workflow verbs, no project parameter

The agent drives everything through aeo keywords — one CLI group, one SDK namespace, on Berlin's /aeo route. The token carries the project, so no call ever takes a project parameter. Nothing about embeddings, index files, prototypes or storage layout leaks through: status answers "what state is this brand's classification in", not "what files are on disk".

What is absent is the point. Upload, topic sync, build and the scoring that rides on the build have no verb here — by design, not by omission. Topic sync and build are the ones worth stating outright: they exist, an agent can read their results, and an agent cannot cause either. An agent that could build would be an agent that could quietly re-stamp the version every existing assignment was measured against.

Only two things in the whole pass wake a machine — the build, and assign. Everything else is answered by the proxy from shared storage. And assign is called twice per pass rather than once per batch: the second call is not a repair, it is how tier-3 judgments sitting in the verdict store get written onto keywords. That is the property to defend — an agent alternates a read and a write dozens of times per pass, and a container start inside that loop would cost more in machine-minutes than the labelling costs in tokens.

Every call carries the topic-set version, and a stale one is rejected loudly rather than silently mixed into the current era. The agent cannot resolve staleness on its own — syncing is a human's button — so the rejection is also the handoff: it stops and says the topics moved.

Where it lives

One directory per brand, on the shared volume

There is no keyword table in Postgres and we are not adding one: a brand's corpus runs to millions of rows, and keyword text is the only identity a keyword has. Everything a keyword accumulates lives in stores keyed by that text, beside the append-only inventory rather than as columns on it — which is what lets those be written and rewritten without the inventory ever being edited.

Jobs can live on different machines exactly when their write sets do not overlap. Every file above has one writer:

The upload is the only entry that reads what it writes, so it is the only one needing ordering rather than just a single writer — which the proxy's per-brand single-flight lock provides. Everything else appends or replaces a file nothing else touches.

One more detail worth knowing before you read anything on disk: the manifest a build writes carries its own leaf topics, in prototype row order, rather than deferring to the pull for them. A later sync can rename or reorder topics at any time, and a reader that took its column names from a newer pull would label one build's vectors with another build's topics.

Rule · two writers would be one too many

The intent store has exactly one writer: the proxy. The verdict store, the same.

The UI uploads keywords to the worker and intents to the proxy as two calls rather than one, and the worker serves the two intent reads for a local checkout but never the write. Two implementations of a read can drift harmlessly; two implementations of a write corrupt a store.

The load-bearing rules

Five sentences that decide most arguments

If you remember nothing else from this page, these settle the majority of "where should this go?" questions before they turn into a design discussion.

01 · Placement, on two axes that must not be welded

What may write derived data: only an explicitly triggered job — never ingestion, never a read. Which machine: the GPU if and only if the job runs the embedding model over the corpus.

The first is an ownership rule; the second is hardware economics. Welding them into "the build writes derived data, and the build runs on the GPU" makes the card read as a permissions boundary, and every new piece of derived data then has to argue for hardware it does not need. assign is the proof they are separate: derived, so explicitly triggered; no model, so no card.

02 · Scoring

Scoring never gets its own trigger, its own job or its own machine — it is the last thing the build does before it exits.

Both things that can invalidate a score — new keyword vectors and a new topic set — are steps of that same build, settled before the score is computed. By the time anyone hands the brand to an agent, the scores are already sitting there.

03 · Ownership

The human owns what the corpus and the topics are; the agent owns what the keywords mean.

Upload, sync and build are buttons on a screen that shows what will change. assign is the one derived job the agent triggers, and it stays that way because its only judgment — the precision target — is agent context, and a button would have to invent or persist that number.

04 · Nothing derived happens by surprise

Ingestion writes down what it was given and stops.

That is what gives every derived file a single writer, which is in turn what lets these jobs sit on different machines with no lock between them. The one exception proves it: the keyword upload reads what it writes, so it gets ordering from the proxy's per-brand single-flight lock.

05 · Cost

Every cost is paid once per keyword, full stop.

Uploads append; builds skip what is indexed; scoring skips what is scored; verdicts are cached per (keyword, topic fingerprint) so post-processing skips what is processed. Nothing in the pipeline can wipe accumulated work — the old "rebuild" flow is gone from the code, and keyword deletion, if it is ever needed, will be an explicit admin operation rather than a side effect.

search intent shipped early

Search intent jumped the queue, for a reason specific to it: most of it arrives free. A Semrush export already carries an intent column, so those keywords are answered during upload before anyone pays for a token; only keywords from Search Console, a hand-written list or a competitor export need an LLM. The vocabulary is closed and it is Semrush's four — commercial, informational, navigational, transactional — and a keyword may carry more than one, so the question asked of an LLM is per-intent, never "pick one".

The accuracy flywheel

The classic weakness of classification is that wrong assignments are invisible. A noise bin is visible; a misfiled keyword is not.

Phase 4 converts that into a measured number. The attribute pass already puts each keyword in front of an LLM, so it adds one nearly-free question — "this was filed under topic X — does that look right?" A no is never silently re-filed; it goes back through tier 3, and we log which tier made the original call. Because bars are derived from the verdict store rather than passed in, assign then gets better on its own: the same call at the same target, run after a few thousand confirmed examples have accumulated, fits tighter bars without anyone re-tuning anything.

Reference

The words we use internally

These appear throughout the codebase, the CLI help and the playbooks. Dotted terms above link here.

Prototype
The vector that stands for a topic. Not the name alone — a name is a weak anchor — but name plus description embedded together, and later a few confirmed example keywords. One per leaf topic, all of them in prototypes.npy.bifrost/core/classification.py · embed_prototypes()
Sweep
Walking a candidate bar down a topic's labelled scores and measuring, at each stop, the precision you would get. The output is the lowest bar that still meets the target. Not a search over a model — just a sorted walk over a few hundred yes/no answers, each one weighted by the band it was sampled from so the number describes the corpus rather than the shortlist.bifrost/core/calibration.py · internal/classification/calibration.go
Bar
The score a keyword must clear to be filed under a topic. One per topic, derived by the sweep at a named precision target, then shrunk toward the brand-wide bar in proportion to the evidence behind it. Never hardcoded, never stored.TopicBar{ Bar, Precision, OwnBar, Labels, Shrinkage, Thin }
Margin
The gap between a keyword's best topic and its runner-up. A big margin means "clearly this topic"; a tiny one means "could be either". The margin bar stays global at 0.01 — a margin is a comparison between two topics, so it belongs to neither and there is nothing per-topic to fit.marginBar = 0.01
Verdict
One LLM answer to one question: does this keyword belong to this topic — yes or no? Stored with the score it was judged at. Three loops write them (calibration, tier 3, verification) and they are the same fact in all three; what differs is only who reads it.bifrost/core/verdicts.py · sources: calibration | tier3 | verification
Fingerprint
A hash over exactly the content that would invalidate downstream work — a topic's name, description and parentage — and nothing that would not. Two scales: one per topic (what labels are filed under) and one for the whole set (what prototypes, scores and assignments are keyed to).backend/internal/topicset/topicset.go
Topic-set version
A counter (v3) stamped when the set-wide fingerprint moves. Content decides what is still valid; the version is what a person can read and what eras are ordered by — which a content hash cannot give, since a revert produces an older hash.classification/topic_set.json · topic_set_version
Shrinkage
Blending a topic's own measured bar with the brand-wide one, weighted by how many labels back it: w = 20/(n+20). Continuous, so there is no minimum-label cutoff to argue about. A topic below 40 labels is additionally reported as thin, purely so a reader knows which numbers to trust.shrink() — mirrored in Python and Go
Leaf topic
A topic that actually competes for keywords: every child, plus any parent with no children. A parent with children never gets a prototype — it would near-duplicate its own children's, and its keyword set is the union of theirs anyway.topicset.Topic.Leaf
Topic health check
Every prototype against every other, run as step one of a build (it used to ride the topic sync, which is also when it embedded prototypes; both moved). Pairs above 0.95 cosine are reported as near-duplicates. A warning, never a decision — merging topics is an edit in the product. Near-duplicate topics are the single most common way a whole corpus ends up ambiguous, and a warning here is a stop sign for calibration.DUPLICATE_SIMILARITY_THRESHOLD = 0.95 · reported to the human who pressed Build
Matmul
Matrix multiply. Because keyword vectors and prototypes are both L2-normalised, the dot product between them is the cosine similarity — so scoring the entire corpus against every topic is a single multiply, chunked 50,000 keywords at a time to bound the working set.SCORE_CHUNK = 50_000
HNSW graph
The approximate-nearest-neighbour index the keyword build produces (ann_hnsw.bin). Tier 2 reads it: a keyword that falls short of its bar inherits a topic when its confidently-assigned neighbours strongly agree — free, and it catches vocabulary the topic name does not share ("zero drop" → Running Shoes). It is also what decides where assign runs: hnswlib keeps the vectors inside the index, ~4.6 KB per element, so a million keywords is ~4.6 GB against the proxy's 2 GB.build/latest/kw/ann_hnsw.bin · M=64, dim=1024
Veto
A recorded no outranks a score above the bar and a neighbourhood agreeing, at every tier. It rules out the (keyword, topic) pair, not the keyword: a denied runner-up drops the second topic, a denied primary sends the keyword to the tiers that ask rather than infer, and the runner-up is never promoted in its place._tier_one() / _denied() in assignment.py
Topic pull
Berlin's topic payload as sent, written verbatim to topic_pull.json by the proxy when someone presses Sync topics. Distinct from topic_set.json, which is what a build actually embedded and names the pull it came from. Comparing the two answers "is a build due?" from two local files.classification/topic_pull.json
Stratified sample
A sample drawn at deliberately different rates from different slices of a population — here, 10/20/40/20/10 across a topic's five score quintiles. It buys more information per label than a uniform draw, but you can no longer just count: each label has to be weighted by its slice's share of the population over its share of the sample, or the measurement describes the sample rather than the corpus._weigh() / weigh() — mirrored in Python and Go
Sampling band
Which score quintile of a topic a shortlisted keyword was drawn from — band 0 is the highest-scoring fifth, band 4 the lowest. The scoring pass stamps band and band_share onto every pool row; verdicts copies both onto the label. A label without them is not evidence and is dropped from the sweep._band_of(rank, total) in scoring.py
Sample pool
Up to 400 candidates per topic, written by the scoring pass and interleaved across five score bands (10/20/40/20/10%). Each row carries its band and that band's share of the topic, so the sweep can weight the labels back to the corpus. sample serves prefixes of it, which is what keeps that call a free read instead of a corpus scan.POOL_PER_TOPIC = 400 · BAND_WEIGHTS = (1,2,4,2,1)
Noise bucket
Keywords that belong to none of the topics this customer tracks. Not "the algorithm gave up" — an honest and often large answer, because fifteen topics do not span a million-keyword corpus. A keyword forced into the nearest of fifteen buckets is worse than one left out of all of them.the remainder after tiers 1–3
Scale-to-zero
The GPU machine runs only while a build does, then shuts down. It is why builds are pinned to the GPU without hesitation — we pay for minutes, not for a card sitting idle — and why waking one to answer a read would cost more than the read.handlers/placement.go · gpuPaths
